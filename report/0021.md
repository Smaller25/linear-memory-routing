# 0021 — Multi-key failure confirmed on the real frozen model; mechanism localization (2026-07-09)

Investigating **why frozen SSC fails multi-key** (hypotheses in `notes/descriptor-hypotheses.md`). The
long-gdn frozen GDN-1.3B + trained-SSC + RULER infra is not in this environment (checkpoints/data are
gitignored, on the campaign machine). But the standalone repo already has a working frozen-SSC pipeline
from the 0009/0014 session: `state-spaces/mamba2-370m` (cached) + trained head `ckpt/ssc_370m.pt`
(low-rank 64, chunk 256, top-k 2) + `data/ruler/*/{niah_single_1,niah_multikey_2}`. So we measured
multi-key on the **real frozen model here**.

## Result — real frozen mamba2-370m, RULER (max-examples 50)
| task | length | vanilla | +RM | **+SSC** |
|---|---|---|---|---|
| niah_single_1 | 2048 | 0.691 | 0.681 | **0.734** (+0.04) |
| niah_single_1 | 4096 | 0.695 | 0.105 | **0.779** (+0.08) |
| niah_multikey_2 | 2048 | **0.452** | 0.419 | **0.129** (−0.32) |
| niah_multikey_2 | 4096 | 0.165 | 0.072 | 0.113 (−0.05) |

**SSC helps single-needle and HURTS multi-key** — vanilla 0.452 → +SSC 0.129 at 2048 (−0.32). This
reproduces established-fact A5 (SSC < vanilla on multi-key) on the real frozen model in this
environment, on mamba2-370m (long-gdn's number was GDN-1.3B; same pattern). +RM (residual memory) is
worse still. The single-needle win + multi-key regression is the exact gap the program must close.

## WHY single works but multi fails — the query-conditioned routing probe
The pooled-descriptor AUC probe is query-INDEPENDENT and cannot explain the gap (multi's difficulty is
query-DEPENDENT: *which of the K key-chunks does THIS query want*). The **routing probe**
(`lmr/analysis/routing_probe.py`, job 1631) measures exactly that from the trained SSC router's own
scores (`router(x_answer)·descriptor_chunk`) at the answer position, per layer: is the queried key's
chunk the router's #1, among ALL chunks vs among only the K key-bearing chunks.

| task | mean #key-chunks K | top1 among ALL (mean / best-layer) | **top1 among KEY-chunks** (mean / best) | chance (1/K) |
|---|---|---|---|---|
| niah_single_1 @2048 | 1.0 | 0.26 / **1.00** | **1.00** / 1.00 | 1.00 |
| niah_single_1 @4096 | 1.0 | 0.20 / 0.97 | **1.00** / 0.97 | 1.00 |
| niah_multikey_2 @2048 | 7.8 | 0.16 / **0.27** | 0.16 / **0.27** | 0.13 |
| niah_multikey_2 @4096 | 15.9 | 0.07 / **0.18** | 0.07 / **0.18** | 0.06 |

**The explanation, cleanly:**
- **Single works because there is ONE key-chunk.** No "which-key" problem; the best retriever layer
  routes to the single needle chunk at **~1.0**. (Mean is low because only a few layers specialise — H6.)
- **Multi fails because the router cannot pick the queried key among the K key-chunks.** Best-layer
  top-1 is **0.27** (K≈8) / **0.18** (K≈16) — only ~2× chance, vs single's 1.0 — and mean is ~chance.
- **The confusion is between KEY-chunks, not with filler.** `top1_amongkeys == top1_all` at every multi
  cell: removing the filler chunks does **not** help, so the queried key-chunk is out-ranked by *other
  key-chunks*, not by filler. This is **H2 (query-independent / query-unconditioned descriptor)** — the
  descriptor says "this chunk has a key-value" but not "this chunk has the key THIS query wants."
- **It worsens with more keys** (0.27 @K=8 → 0.18 @K=16), matching the length-scaling collapse (A7).

So the multi-key failure is **localised to routing (H2)**: with query-independent pooled descriptors the
router can't disambiguate which key-chunk the query wants. (Whether within-chunk *extraction* adds
further loss is a separate, downstream test — E-B oracle-routing — not yet run; but routing alone is
already the binding constraint here, at ~2× chance.)

The earlier **from-scratch raw-dot probe (1610/1611) was inconclusive** (near-random everywhere): it
scored by raw `query·hidden`, reproducing only the "cos-sim is random" fact (disc_ratio 1.002); the
signal needs a learned projection — which is exactly what the routing probe above uses (the trained
router). Superseded.

## Bottom line
Multi-key fails because **routing is query-unconditioned** (H2): the pooled per-chunk descriptor
identifies "a key-chunk" but not "the key THIS query wants", so among K similar key-chunks the router
lands on the right one only ~2× chance (and worse with more keys). Single is trivially immune (K=1).
This is a routing/descriptor-design limit, **not** a within-chunk capacity limit (the info is present;
routing can't select it). The fix direction implied: make routing **query-conditioned** — late-
interaction (MaxSim over per-key vectors) so the queried key is matched at read time, without
collapsing a chunk to one query-independent vector. (Frozen cache is already O(N), so multi-vector is
admissible here — 0019's O(1) objection doesn't apply on Track A.)
