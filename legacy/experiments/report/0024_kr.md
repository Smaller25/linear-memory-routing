# 0024 요약 (한국어) — MC-SSC(mean-pool) GDN2-370M은 왜 multi-NIAH에 실패하는가: **routing이 지배적 병목** (2026-07-26)

> 원문: [`0024.md`](./0024.md). 수치·재현 커맨드의 원본은 영문 보고서를 따른다.

## 한 줄 결론

Memory-Caching SSC(mean-pool descriptor)를 얹어 end-to-end 학습한 GDN-2 370M이 multi-key NIAH에서
무너지는 원인을 **write → read → route → 생성** 4단계로 분해한 결과, **state에 정답은 온전히
쓰여 있으나(write ✓), mean-pool descriptor가 "여러 key 중 어느 segment인가"를 구분하지 못해
(route ✗) 실패한다.** 정답 chunk를 top-k에 강제 주입하는 oracle 개입만으로 4/4 셀 전부 점수가
오르며(최대 0.062→0.562), 이것이 routing 병목의 **인과적** 증거다. 단, distractor가 gold와
같은 segment를 공유하는 경우(S)에는 routing이 아니라 **read-side 구분 실패**가 섞여 있다.

## 셋업 요약

- **모델**: `mc-gdn2-370m-...-v2-meanpool`의 5B/30B ckpt (`mc_370M`: 16 layers, topk=2,
  chunk 256, descriptor = L2-norm key mean-pool). vanilla-5B는 loader 검증용.
- **코드 고정**: long-gdn worktree `e71713e`, fla `4b02d15d` pin (그 이후 fla는 GLA API 비호환).
- **데이터** (2048 tokens = 8 segments): Dataset A = RULER 표준 single_1/multikey_1 각 50개;
  Dataset B = single/multi **쌍맞춤** 32쌍 — 조건 **S**(distractor를 gold와 같은 segment에 강제) /
  조건 **D**(전부 다른 segment). 쌍은 distractor 자리만 다르고 토큰 단위로 동일.
- **앵커** (collaborator 공식 평가, 재측정 안 함): @2K S-NIAH-1 / MK-NIAH-1 =
  vanilla-5B **90/20**, MC-5B **60/2**, MC-30B **92/32**.

## E1 — routing 정확도 (정답 chunk를 찾는가?)

answer position에서 16개 layer의 SSC routing 점수를 재계산. **chance level은 데이터셋마다 다름**
(multikey는 컨텍스트가 짧아 chance 0.486; single/paired는 0.286–0.288).

| best-layer hit@2 | single_1 | multikey_1 | paired-S | paired-D |
|---|---|---|---|---|
| mc-5B | **0.933** | 0.660 | 0.812 | **0.562** |
| mc-30B | **1.000** | 0.809 | 0.750 | **0.500** |

- single routing은 사실상 해결(chance의 3.2–3.5×); multikey는 자기 chance 대비 1.4–1.7×에 불과.
- **D 조건이 최악**: gold의 평균 rank ≈ 2 (top-2 밖). key 보유 segment들 사이에서 질의된 key를
  고르는 `amongkeys`는 ≈0.5 (**동전 던지기 수준**), D에서는 0.19/0.375로 오히려 distractor
  segment를 선호.
- router는 "key가 있는 segment vs 없는 segment"는 구분하지만 "**어느 key인가**"는 구분 못 함.
- single의 routing 신호는 마지막 1–2개 layer에 집중; multikey는 평평한 프로파일.

## E2 — oracle routing 개입 (인과 주실험)

전 layer에서 gold segment를 top-k에 강제 주입(gate에서 불리하지 않도록 score = max(선택 최대,
online)). `gold=None`이면 stock 모델과 **byte-identical** 생성임을 확인한 위에서 측정 (n=16/셀).

| model | S: baseline→oracle | D: baseline→oracle |
|---|---|---|
| mc-5B | 0.125 → 0.312 (+0.188) | 0.188 → 0.500 (**+0.312**) |
| mc-30B | 0.000 → 0.312 (+0.312) | 0.062 → 0.562 (**+0.500**) |

- **4/4 셀에서 oracle > baseline** — routing만 고쳐도 실패의 큰 덩어리가 정답으로 이동.
- E1이 routing 최악으로 지목한 **D에서 회복이 가장 큼** (일관성).
- **30B도 해소 못 함**: 30B는 routing이 좋아지고 앵커도 2→32로 오르지만 oracle 여유분이
  오히려 더 큼 → 토큰 스케일링은 router를 개선할 뿐 병목 지위를 바꾸지 못한다.
- oracle이 포화하지 않음(0.31–0.56): 잔여 실패는 read-side + gate/생성 몫.

## E3 — layer별 write/read fidelity (state/decoding 실패인가?)

생성 없이 prompt 1-pass로, 학습과 동일한 `chunk_gdn2` 경로로 state를 재구성해 `r = q·M`을 분해.

- **Write는 무죄**: `b1_after`(value 직후 재독출) 0.67–0.97, 모든 layer ≥0.5, single vs multi
  차이 ≤0.021 — 붕괴 없음. (단 S 조건 비교는 "filler vs distractor" 비교라는 범위 주의.)
- **segment 내 침식은 실재** (S/D 무관): `b1_final ≪ b1_after` (0.78→0.44) — value 이후의
  write들이 segment 끝까지 가며 가독성을 깎음. multi-key 실패가 아니라 아키텍처 비용.
- **Read는 S에서만 깨짐**: multi의 answer-position 읽기를 쌍둥이 single과 비교한
  `b2_read_cos_vs_single`이 S에서 layer 깊어질수록 0.911/0.903까지 하락, **D는 전 layer ≥0.98**.
  같은 key의 distractor가 같은 segment에 있으면 write는 멀쩡한데 **읽어낸 내용**이 흔들림.
- 절대 지표 주의: `interf_ratio`는 어디서나 >1 (단일 binding 항이 소수), `qk_align` ≈ 0 —
  통제된 쌍 비교만 신뢰 신호.

## 판정표

| 단계 | 판정 | 핵심 근거 |
|---|---|---|
| write | **✓ 온전** | b1_after ≥0.5 전 구간, single/multi Δ ≤0.021 |
| read | **부분 ✗ (S만)** | S에서 read-cos 0.91까지 drift, D는 ≥0.98 |
| route | **✗ (D 최악)** | paired-D hit@2 0.50–0.56 (chance 0.286), amongkeys ≤ 동전 |
| oracle 회복 | **✓ 전 셀** | 최대 +0.500 (mc-30B/D) |

**최종 판정 = spec row 3 "routing 실패"가 지배적** + S 조건에 국한된 row-2(readout) 혼입 +
oracle로 안 고쳐지는 잔여 gate/생성 성분.

## 개선 알고리즘 시사점 (두 갈래, 상호 대체 불가)

1. **Cross-segment key 선택 (D) — 수익 큰 레버**: key 정체성을 평균으로 뭉개지 않는 descriptor
   (multi-vector/per-key descriptor, query-conditioned scoring, 또는 key들이 segment를 공유하지
   않게 하는 finer chunking). oracle 개입이 시뮬레이션한 것이 바로 이것.
2. **Within-segment key 충돌 (S)**: routing으로는 원리적으로 불가 — **state 수준 read-side
   구분**(per-key slot, 선택된 segment 내부의 query-conditioned 2차 read)이 필요.

report 0010의 "segment-level routing은 한 segment에 뭉친 key를 구분 못 한다"는 스코프 진술이
routing 성분(인과적으로 지배적, 수리 가능)과 readout 성분으로 분해된 셈.
