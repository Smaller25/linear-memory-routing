# 0019 — Axis-2 hierarchical re-compression: lossy merge loses to dropping for exact recall (2026-06-28)

0011 showed the flat segment cache is **not constant-memory**: cap it to B segments and recall degrades
∝ B/N. Axis-2's proposal: instead of *dropping* old segments, **compress** them — keep B/2 recent
segments fine, merge the older ones into ≤B/2 coarse slots via a learned adjacent-pair conv (recursive
halving = a balanced merge tree; cf. Compressive Transformer). Bounded memory at B, distant info
preserved lossily rather than dropped. Test under oracle boundaries (clean cuts isolate the cache
policy) and density boundaries (0018), irregular MQAR, same recipe as 0015 (GDN-2 d256/4L).

## Result (recall acc vs #kv = N segments; budget B in the row name)
| oracle boundaries | kv64 | kv128 | kv256 |
|---|---|---|---|
| **full** (O(N) ceiling) | 0.999 | 0.988 | 0.873 |
| capped-64 | 0.984 | 0.491 | 0.236 |
| **hier-64** | 0.732 | 0.263 | 0.032 |
| capped-32 | 0.513 | 0.256 | 0.122 |
| **hier-32** | 0.394 | 0.109 | 0.015 |

| density boundaries (0018) | kv64 | kv128 | kv256 |
|---|---|---|---|
| full / capped-32 / hier-32 | ~0.00 | ~0.00 | ~0.00 |
| capped-64 / hier-64 | 0.20 / 0.22 | ~0.00 | ~0.00 |

## Findings
**1. Capped reproduces the 0011 ∝B/N degradation.** With budget B, recall falls as N grows past B:
capped-64 = 0.98 (N=64=B, nothing dropped) → 0.49 (N=128, half dropped) → 0.24 (N=256). Exactly the
"not constant-memory" curve. capped-32 is uniformly lower (smaller budget).

**2. Hierarchical compression is WORSE than dropping — not better.** At every matched budget,
**hier < capped** (hier-64 0.73/0.26/0.03 vs capped-64 0.98/0.49/0.24; hier-32 < capped-32 likewise).
The reason is fundamental to *exact* recall, not an under-trained merge: merging two distinct facts
into one coarse slot makes **neither recoverable**. capped keeps B facts *exactly* (drops the rest);
hier keeps only B/2 exact and spends the other B/2 slots on lossy merges of the older facts — which the
read-out then cannot resolve to a specific needle. Trading exact slots for lossy ones strictly hurts
when the query needs an exact token. (The merge_conv is co-trained; gradient cannot conjure a lossless
2→1 compression that doesn't exist.)

**3. Density boundaries make the cache-policy question moot.** With the 0018 (drifted) density
boundaries, recall is ~0 under every policy — the cache holds the wrong segments to begin with, so how
you budget them is irrelevant. This confirms axis-2 presupposes good boundaries, which only the
supervised/oracle route currently provides.

## Verdict
Hierarchical re-compression does **not** solve the constant-memory problem for **exact multi-key
recall**: lossy coarsening destroys the precise needle the task asks for, so it loses to simply keeping
fewer exact slots. **0011's conclusion stands** — exact multi-key recall is fundamentally ~O(N) in the
number of facts. Compression is the right tool only where distant memory may be *lossy/aggregate*
(summarization, semantic retrieval, soft attention) — not where every fact must be recovered verbatim.
This bounds the scope of the whole program: the segment-cache read-out wins (0005/0012/0017) but its
memory cost is intrinsic to exactness; you cannot compress your way to constant memory on exact recall.

## What would change the result
- A **retrieval-not-merge** budget: keep all N as compact *keys*, but materialize only the top-B
  *values* on demand (compress the index, not the payload) — sidesteps the lossy-merge problem.
- Re-test hier on a **lossy-tolerant task** (e.g., long-context summarization / aggregate queries),
  where a coarse distant summary is sufficient — its natural home.
